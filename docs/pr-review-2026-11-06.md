# PR review: 2026-11-06

Reviewed and integrated PRs #52–#61. These changes are included in the 0.5.0 release.

## Repairs and behavior

- #52: `CachedReadinessProbe` is a manually populated snapshot cache, distinct from the existing active `ReadinessProbe`. Validate TTL, copy input/output, expire at the exact boundary. `getCachedOrStale()` returns null when expired despite its historical name. No new Kubernetes route is installed.
- #53: `isValidCorsOrigin` accepts serialized HTTP(S) origins only. Wildcard does not authorize credentialed requests; explicit origins may. The optional third argument defaults to false (no credentials).
- #54: `TokenBlacklist.revoke` accepts Unix milliseconds. `revokeJwt` explicitly converts JWT exp seconds. Expired records are reclaimed on writes, capacity defaults to 10,000, and a full store throws rather than evicting a live revocation. Callers must fail closed on capacity errors. Re-revocation cannot shorten an existing expiry. State is local to the process and is lost on restart.
- #55: `matchSubdomainOrigin` requires a serialized HTTPS origin and a full hostname regex match. Copies regex state and removes global/sticky flags. Callers remain responsible for their allowlist pattern and any port restrictions; this helper does not hardcode Kite domains.
- #56: settlement notifications preserve large atomic amounts via bigint/string and reject unsafe numeric amounts. Events are frozen snapshots. This is a synchronous EventEmitter: listener errors propagate, listeners need explicit removal, events have no persistence, deduplication, or delivery guarantee. Do not allow a notification exception to retry an already settled payment.
- #57: fee tiers and returned client records are copied, preventing external mutation of retained pricing/volume state.
- #58: stage cache replacements before eviction so an invalid write cannot destroy a valid entry. Existing privacy/size limits remain in force.
- #59: settlement reconciler binds to one network, inferred from its first receipt or supplied to its constructor. The binding survives clear; use a separate instance per network. This prevents mixed-chain totals and transaction-hash collisions across networks.
- #60: reuse the bounded `SlidingWindowLimiter`; require a trusted `keyGenerator` instead of trusting forwarding headers. Validate options, emit Retry-After, reject missing identities. Despite its inherited name, `adaptiveRateLimiter` implements a fixed sliding-window budget, not dynamic adaptation. The options type is `AdaptiveRateLimiterOptions` to avoid colliding with the existing public limiter type.
- #61: strict 64-character hex HMAC-SHA256 verification, minimum 32-byte secret, strict Unix-millisecond timestamp validation. Raw-payload mode matches `WebhookDispatcher.signPayload`. When a timestamp argument is supplied, sender must sign `timestamp + "." + payload`; changing an unsigned timestamp cannot refresh an old signature. Existing dispatcher sends raw-payload signatures without a timestamp header. Callers must deduplicate event IDs and, in raw mode, separately validate a timestamp inside the authenticated payload if freshness is required.

All new utilities are public exports but require explicit application integration. Existing proxy routes, JWT authentication, CORS settings and settlement dispatch are not automatically changed by importing them.
